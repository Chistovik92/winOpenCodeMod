# winOpenCodeMod — план разработки

Модификация для OpenCode Desktop: GUI-интерфейс для добавления/редактирования/удаления
кастомных LLM-провайдеров «руками», без правки JSON и без скриптов.

## 1. Ключевой архитектурный вывод

Отдельную программу запускать **не нужно**. OpenCode Desktop (Electron-приложение) имеет
официальную систему расширений — **GUI-плагины** (`@opencode/plugin/gui`). Плагин можно
«встроить» прямо в интерфейс основного приложения:

- добавляет собственную **страницу в Настройках** (Settings page);
- добавляет команды в командную палитру;
- добавляет панели, пункты меню и т.д.

То есть наша «модификация» = **плагин-пакет**, который:
1. имеет GUI-часть (интерфейс на Solid.js) — страница управления провайдерами;
2. имеет server-часть (логика) — чтение/запись провайдеров через RPC.

Пользователь ставит плагин одной строкой в глобальном `opencode.json(c)` — и в десктопе
появляется страница управления провайдерами. Без форка репозитория, без пересборки
Electron, без отдельного процесса.

### Два варианта реализации (что значит «модифицирует основное приложение»)

| | A. GUI-плагин (рекомендуется) | B. Форк исходников |
|---|---|---|
| Суть | официальный extension point `@opencode/plugin/gui` | править `packages/…` в репо anomalyco/opencode, пересобирать десктоп |
| Отдельная программа | нет | нет |
| Пересборка Electron | не нужна | нужна (тяжело, свой форк поддерживать) |
| Риск поломки при обновлении OpenCode | низкий (API, но experimental) | высокий (конфликты при rebase) |
| Установка у пользователя | `plugins: ["./winOpenCodeMod"]` | своя сборка приложения |

Вывод: идём по **варианту A**. Это именно «встроить в интерфейс основной программы».

## 2. Что меняет эта модификация в основной программе

Пользователь видит в десктопе:

1. **Настройки → «Провайдеры» (Custom providers)** — новая страница:
   - список кастомных провайдеров (имя, package, baseURL, список моделей);
   - кнопки «Добавить», «Изменить», «Удалить».
2. **Форма добавления/редактирования провайдера**:
   - ID/префикс провайдера (`acme` → модели `acme/model`);
   - display name;
   - `package` (выпадающий список встроенных пакетов: `openai-compatible`, `anthropic`,
     `anthropic-compatible`, `openai`, `google`, `azure`, `amazon-bedrock`, `openrouter`,
     `xai`, и произвольный npm-пакет / `file://`);
   - `baseURL` (endpoint);
   - `env` (имя переменной окружения для ключа) или прямой ввод API-ключа;
   - `headers`, `body` (дополнительно);
   - список моделей: для каждой — ID модели, отображаемое имя, `modelID` (что уходит
     провайдеру), опционально `limit`, `cost`.
3. (опционально) команда палитры `winOpenCodeMod:open` для быстрого открытия страницы.

После сохранения провайдер сразу доступен: модель выбирается как `acme/model` через
`/models` (или аналог в десктопе), без перезапуска.

## 3. Хранение данных (persistence) — главное решение

Кастомные провайдеры в OpenCode V2 задаются ключом `providers` в `opencode.json(c)`:

```jsonc
{
  "providers": {
    "acme": {
      "name": "Acme",
      "env": ["ACME_API_KEY"],
      "package": "@opencode/ai/providers/openai-compatible",
      "settings": { "baseURL": "https://llm.acme.example/v1" },
      "models": { "qwen3-coder": { "name": "Qwen 3 Coder" } }
    }
  }
}
```

Есть два способа, как плагин может «материализовать» провайдеры:

### Вариант 1. Runtime-трансформация + собственное хранилище (рекомендуется)

Server-часть плагина при старте читает определения провайдеров из **своего** файла
(или `ctx.storage`) и регистрирует их через официальный API:

```ts
await ctx.provider.transform((editor) => {
  editor.add({
    info: {
      ...Provider.Info.empty(Provider.ID.make("acme")),
      name: "Acme",
      activation: "enabled",
      package: "@opencode/ai/providers/openai-compatible",
      settings: { baseURL: "https://llm.acme.example/v1" },
    },
    models: [{ ...Model.Info.default(Provider.ID.make("acme"), Model.ID.make("qwen3-coder")), name: "Qwen 3 Coder" }],
  })
})
```

**Плюсы:** полная изоляция — не трогаем пользовательский `opencode.json`, не рискуем
повредить его комментарии/прочие настройки; кросс-платформенно; переживает рестарт.
**Минусы:** провайдеры «живут» только пока плагин загружен; их не видно в `opencode.json`;
API-ключи лежат в нашем хранилище (нужно аккуратно: храним в `ctx.storage`, помечаем поле
как секрет, по желанию используем `env` вместо прямого ключа).

### Вариант 2. Запись в конфиг-файл (канонично, но рискованнее)

Server-часть читает/пишет `~/.config/opencode/opencode.json` (глобально) или
`.opencode/opencode.json` (проект), мержит ключ `providers`, сохраняя прочие настройки.
OpenCode сам перечитывает конфиг после сохранения (файл «watch»).

**Плюсы:** провайдеры видны в конфиге, каноничный путь, ключ можно задать как
`{env:VAR}` (секрет не в конфиге).
**Минусы:** нужно **сохранять JSONC-комментарии и форматирование** (наивный
`JSON.parse`/`stringify` их уничтожит), риск повредить чужой конфиг, нужна аккуратная
стратегия мержа.

**Решение:** берём **Вариант 1** как основной (безопасный, изолированный), а как
дополнительную кнопку — «Экспорт в opencode.json» (генерирует готовый JSON-блок, который
пользователь может вставить сам, если захочет каноничную запись). Финально подтвердим
на этапе проектирования.

## 4. Технологический стек

- **Язык:** TypeScript.
- **GUI:** Solid.js + `vite-plugin-solid`, сборка через пресет `@opencode/plugin/gui/vite`
  → один CommonJS-бандл `dist/gui-experimental.cjs`.
- **Server-часть:** `@opencode/plugin` (Plugin.define, `ctx.provider.transform`,
  `ctx.storage`).
- **RPC-контракт:** `@opencode/plugin/rpc` (методы list/add/update/remove).
- **Пакеты:** `@opencode/plugin` (dependency), devDependencies: `vite`,
  `vite-plugin-solid`, `solid-js`, `@types/node`.

Важные ограничения (из доков GUI):
- GUI-часть должна быть **одним предсобранным CJS-файлом**; в него инлайнится всё, кроме
  общих модулей (`effect`, `solid-js`, `@opencode/*`, `electron`, `node:*`).
- Экспорт части называется `./gui-experimental` (API **experimental**, может меняться).
- Десктоп читает плагины только из `opencode.json(c)` (не из `cli.json`).
- Зарезервированы id в namespace `opencode.*` и id самого приложения — наш id должен быть
  уникальным (например, `winopencodemod`).

## 6. Этапы (MVP → полировка)

1. **Скаффолд.** `package.json`, `vite.config.ts`, минимальный GUI-плагин, который
   добавляет пустую Settings-страницу «Провайдеры». Проверяем, что она появляется в
   десктопе (подключаем через `plugins: ["./winOpenCodeMod"]` в глобальном конфиге).
2. **Server + RPC.** `rpc.ts` (list/save/delete), `provider-store.ts` (хранение через
   `ctx.storage`), `register.ts` (transform). Проверяем, что добавленный провайдер виден
   в `/models`.
3. **GUI-список.** Страница показывает сохранённые провайдеры, кнопка «Удалить».
4. **GUI-форма.** Форма добавления/редактирования: базовые поля (id, name, package,
   baseURL, env) + редактор списка моделей.
5. **Провайдер + модели целиком.** Полный набор полей (`headers`, `body`, `limit`, `cost`,
   `modelID`, `type`). Валидация.
6. **Секреты.** Решение по API-ключу: `env`-имя по умолчанию, опция прямого ввода с
   предупреждением (значение хранится в `ctx.storage`).
7. **Полировка.** i18n (ru/en), команда палитры, обработка ошибок, экспорт в
   `opencode.json`, README с инструкцией установки.

## 7. Риски и открытые вопросы

- **Experimental GUI API** — сигнатура `./gui-experimental` и `@opencode/plugin/gui`
  может меняться между релизами; фиксируем версию OpenCode, под которую пишем.
- **Перерегистрация провайдеров** — после изменения данных нужно вызывать
  `ctx.provider.reload()` / re-register transform (доки это явно описывают).
- **Конфликт id** — если пользователь уже задал провайдера с тем же id в `opencode.json`,
  поведение нужно уточнить (наш transform vs конфиг). См. раздел «Ошибки» в /docs/providers.
- **Хранение ключей** — `ctx.storage` хранит JSON как есть; для секретов стоит минимум
  пометить поле и предупредить, либо рекомендовать `env`.
